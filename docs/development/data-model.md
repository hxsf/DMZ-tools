# 数据模型

当前资料收集自 2026 年《现代战争4》DMZ 首发期来源，已接入最小版工具。它不是完整物品库，也没有宣称当前版本游戏实测。收集日期为 2026-11-05，具体出处见 `src/data/sources.ts` 和 [来源登记](../external/mw4-dmz/ATTRIBUTION.md)。

打印配方覆盖本次查阅的 95 项普通打印记录（9 类）；武器手册按社区目录、官方购买目录及用户截图交叉核对，收录 32 种。175 个物品记录包括 111 项物品 / 材料、32 把武器和 32 份手册。`catalog.coverage` 保留 `sample`，表示当前资料范围有限，不作为跨版本游戏总量的承诺。缺少获取条件不会阻止收录或用户手动标记。

## 类型职责

| 文件                       | 内容                                                   |
| -------------------------- | ------------------------------------------------------ |
| `src/types/source.ts`      | 来源、事实声明和冲突声明                               |
| `src/types/item.ts`        | 物品 ID、名称、分类、材料数量                          |
| `src/types/recipe.ts`      | 打印配方、成本、产出与打印前置                         |
| `src/types/unlock.ts`      | 解锁条件、打印能力和武器手册解锁规则                   |
| `src/types/catalog.ts`     | 一批资料及其版本、覆盖范围                             |
| `src/types/progress.ts`    | 用户库存、解锁记录、存档版本                           |
| `src/types/requirement.ts` | 制作目标、单次产量确认、计划状态；保留已有搜集目标契约 |
| `src/types/calculation.ts` | 材料汇总、库存缺口及计算问题                           |

类型文件只定义契约，不引入 Preact 或 Signals。静态资料通过 `satisfies` 接受类型检查；跨记录引用、非负整数等约束仍需运行时检查。用户存档与资料版本分别演进，不把资料复制进每个存档。

## 事实与未知

成本、产量、解锁方式按字段记录 `Fact<T>`，不能用一条总体“已验证”标记覆盖不同质量的信息：

- `reported`：所引来源有记载，附来源 ID；不等于游戏实测。
- `unknown`：尚未找到足够证据，不提供猜测值。
- `conflicting`：保留至少两项有出处的说法，不自动选一个用于计算。

当前 7 项配方的材料成本存在来源分歧，以冲突形式保存：起爆器、爆破炸药、防辐射药、自救包、防弹插板箱、炸弹小飞机和一次性降落伞；稳定 ID 见 [资料说明](../../src/data/README.md#需要继续核对的字段)。网页中的 `+1` 可能只是加入清单按钮，当前未确认每次打印的产出数量，因此保持未知。未记载的现金成本用 `null` 表示；只有明确确认无现金费用才填 `0`。

计算器按“目标成品数量”工作，只计算配方的直接材料，不递归展开中间材料。来源未知单次产量时，用户必须显式填写 `outputPerCraft`；值保存在制作目标中，与公共来源事实分开。打印次数按目标数量除以单次产量向上取整。未知或冲突成本返回待确认问题，不能静默按零成本或其中某个说法继续计算；未知现金费用不显示为免费。

## 物品、配方与解锁

`Item` 区分基础资源、实体材料、装备、武器和武器手册。可选 `rarity: Fact<ItemRarity>` 单独保留普通、精制、稀有、史诗、传奇、终极六档及来源，缺失不等于普通；武器和手册分别记录，不互相继承。基础资源与材料共用 `ItemAmount`，中间材料作为配方产出仍引用同一个物品 ID。名称保留英文和中文来源类别，中文别名仅用于搜索；ID 使用本项目的稳定键，不冒充官方编号。

简体中文是首版面向用户的语言。游戏名称随物品资料保存，界面按钮、状态和提示使用独立的翻译文案。名称缺少中文时回退英文，检索同时考虑中英文与别名。`zhCNOrigin: "official"` 表示名称来自官方文章或实际客户端文字，具体出处见物品 `sourceIds`，不能仅凭这一值推断所有物品已实测。32 把武器已按用户提供的中文客户端截图核对，截图来源单独标记为 `in-game`；其他物品依所引官方、社区或项目资料区分。官网旧译名保留为搜索别名，详见 [名称核对记录](weapon-name-verification.md)。更换译名或界面语言不改变稳定 ID 和用户进度。

界面已通过 `i18next` 和 `react-i18next` 提供 `zh-CN`、`en` 两套翻译，默认 `zh-CN`。图片通过 `src/data/images.ts` 按稳定物品 ID 映射，当前有 143 张真实游戏图片（111 张物品 / 材料、32 张武器）；手册复用对应武器图。署名与出处分别在 DMZHub、DMZTracker、MW4Field 资源目录的 `ATTRIBUTION.md`。缺图只显示名称，不制造替代图。

`Recipe` 表示一项打印定义，分别保存：

1. `output`：打印出的物品和每次产量。
2. `cost`：物品消耗及现金消耗。
3. `unlock`：获得配方的条件，支持等级、任务、搜到后撤离、能力解锁以及 AND/OR 组合。
4. `requires`：制作所需的打印机和打印能力。

获得等级奖励中的一个成品，不代表解锁了其配方；配方已解锁也不代表打印类别或材料制作升级已完成。能力单独记录，例如普通打印机、战场升级打印类别、精制材料打印和史诗材料打印。当前保留 5 项能力定义，未自动推断材料打印升级已完成。已另行收集的 [9 组 34 档永久升级](upgrades-research.md)只是开发参考，数据保存在 [`docs/external/mw4-dmz/upgrades.json`](../external/mw4-dmz/upgrades.json)；运行时类型、解锁界面和需求计算尚未接入升级档位、重复打印进度及其前置关系。

手册物品关联对应武器；`WeaponManualUnlock` 可补充已知的获取机制，但不要求先收集完整条件才能收录手册。配方的 `unlock` 同样是可选资料。手册与配方均由用户手动确认是否解锁，获取条件不限制勾选。通用手册机制、单个手册售价和撤离奖励不是同一事实，不用通则强行填满每条记录。武器外观蓝图和重复手册带来的迷彩进度不在本轮范围。

## 用户记录

`Inventory` 仅记录用户在材料清单中确认的已有数量。不存在的键表示尚未录入，显式 `0` 才表示确认没有；局内尚未撤出的搜集物不直接写进仓库。首版没有独立的材料储备页面。

`UnlockProgress` 分开保存配方、手册和能力的确认状态。没有记录等价于未知，界面归入“待解锁”，不能按等级自动标成已解锁。确认记录带时间，玩家等级单独保存。首版界面只手动修改配方与手册，未提供能力或等级管理。

`RequirementPlan` 类型保留标题、优先级、启用/暂停/完成状态，以及搜集或制作目标契约，兼容已有存档。首版界面只从打印计算器加入制作目标，提供完成、恢复和移除，不提供自由搜集、暂停或优先级编辑。制作目标的 `quantity` 是成品数量，`outputPerCraft` 是来源未知时由用户确认的单次产量。不同目标的相同直接材料先汇总，再共用库存抵扣一次；完成计划后不再计入未完成需求，但不会自动扣库存。

用户存档只保存基础记录，不存 Signals 对象、缺口或完成率。公共 store 使用工厂创建；`createAppState(kv)` 已通过上下文接入页面，协调显式加载、用户操作触发的保存及状态反馈，不自动订阅 store 写入。`loadSnapshot(kv)` 和 `saveSnapshot(kv, snapshot)` 依赖通用 `AsyncKV`，浏览器实现由 `createBrowserKV()` 提供。存档键 `dmz-tools:user`、版本 1 保持不变，新增的可选 `outputPerCraft` 兼容原有 JSON 数据。

应用等待加载完成，区分有效存档、没有存档、无效内容、不支持的版本与访问失败。只有有效恢复或确认键不存在后才允许保存，读取失败不能被默认空值覆盖。`persist()` 调用时固定快照，写入按队列串行执行；存档层在 I/O 前校验并序列化，成功后才返回 `saved`，无效快照不触发写入。界面显示实际保存结果；远端认证、离线同步及多端冲突处理尚未实现。

KV 读写通过 `ts-results-es` 返回 `Result`，加载与保存函数显式处理 `Err`，保留底层 `KVError` 至结果的 `error` 字段。序列化失败单独使用 `invalid-snapshot` 错误码，不与存储访问错误混淆。原始 `cause` 仅用于诊断，不进入用户存档。存档层仍使用 `ready`、`empty`、`unsupported-version` 等有业务含义的状态，避免调用方丢失版本与内容错误的区别。
